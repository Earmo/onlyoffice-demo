# OnlyOffice Document Service

## What This Is

这是一个基于 `Spring Boot + Vue + ONLYOFFICE Docs` 的前后端分离在线文档编辑服务，目标是既能独立部署成一个完整软件服务，也能作为其他分布式系统中的文档编辑微服务被接入。它需要提供文档列表、上传与编辑流程、可插拔存储策略，以及与外部用户体系低耦合的集成能力。

## Core Value

任意上层系统都应该能以低耦合方式接入一个可分布式部署的文档编辑服务，让用户先看到自己的文档列表，再安全地选择、上传、打开并保存文档。

## Requirements

### Validated

- ✓ 浏览器可以通过同源入口打开 ONLYOFFICE 编辑器并编辑默认 `demo.docx` — existing
- ✓ 后端可以为指定文档生成 ONLYOFFICE `config + token` — existing
- ✓ ONLYOFFICE 可以从后端下载文档并把保存结果回调到 Spring Boot — existing
- ✓ 用户可以上传本地文档并切换到新文档继续编辑 — existing
- ✓ 用户可以导入远程文档 URL 并在编辑器中打开 — existing
- ✓ 用户可以在当前光标位置插入远程图片 — existing
- ✓ 页面可以展示最近一次保存回调与落盘状态 — existing

### Active

- [ ] 把当前仓库升级成前后端分离、可分布式部署的文档编辑服务，而不是固定 demo 页面
- [ ] 首页先展示文档列表，用户选择或上传文档后再进入编辑器
- [ ] 引入真实用户上下文，而不是固定演示用户，并且与外部用户体系保持低耦合
- [ ] 建立可插拔存储策略，先接入 MinIO，并为腾讯云 COS / 阿里云 OSS 留出统一扩展接口
- [ ] 让服务既可单独部署，也可被其他系统作为文档编辑微服务集成

### Out of Scope

- 移动 App 客户端 — 当前只规划 Web 服务和微服务集成模式
- 完整企业 IAM / SSO 产品化平台 — 本轮只做低耦合用户接入能力，不做整套身份平台
- 历史版本、复杂协同权限和审计后台 — 不是第一阶段必须交付的核心价值
- 腾讯云 COS 与阿里云 OSS 的正式实现 — 本轮先把策略接口和 MinIO 跑通，其他云存储留到后续阶段

## Context

- 当前代码已经具备前端宿主页、Spring Boot API、ONLYOFFICE Docs 容器与 nginx 同源代理的最小闭环。
- `.planning/codebase/` 已完成 codebase map，明确了现有技术栈、架构、约定、测试和风险点。
- 当前仓库还没有文档列表、用户体系适配层、共享元数据存储或真正面向分布式部署的服务边界。
- 这次新的产品方向明确要求把“演示用最小集成”升级为“可独立部署 / 可嵌入式集成的文档服务”，因此原有偏 demo 的 roadmap 已不再适用。
- 当前已知改造重点集中在五类：服务边界、共享文档元数据、存储策略抽象、用户上下文适配、文档列表与编辑入口重构。

## Constraints

- **Tech stack**: 延续现有 `Spring Boot + Vue + ONLYOFFICE` 作为基础，不推翻已验证的集成主链路
- **Deployment**: 必须支持前后端分离和分布式部署，不能把关键状态绑死在单机文件系统或单实例内存里
- **Integration**: 用户机制必须低耦合，优先通过适配层 / 上下文注入与外部系统对接，而不是把内部认证方案写死
- **Storage**: 存储能力必须策略化，MinIO 是 v1 首个实现，COS / OSS 通过同一抽象后续接入
- **Experience**: 首页默认展示文档列表，用户选择或上传后再打开编辑器，不能继续以固定 demo 文档作为入口
- **Quality**: 新 roadmap 必须覆盖服务化、可集成和可验证三条主线，不能只做 UI 或单点修补
